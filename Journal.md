# Architecture Journal — Configuration-Driven Governed Agentic Delivery Harness

**Version:** 2.0  
**Reference Application:** StoreOps  
**Evidence Run:** SLA Breach Alerting  
**Purpose:** Capture the key architecture decisions, rationale, trade-offs, evidence, and insights observed while designing, building, and exercising the governed agentic delivery harness.

> **Evidence convention:** Repository paths below identify the authoritative design/configuration artifacts and the run-specific evidence generated by the completed SLA Breach Alerting execution. Run-specific files are referenced using `<RUN_ID>` / `<SPRINT_ID>` where the identifier is generated at runtime.

## Architecture Decisions and Build Insights

| Design Decision | Rationale | Trade-off | Repository Evidence | Outcome / Insight |
|---|---|---|---|---|
| **1. Separate delivery into bounded Planner, Generator, Evaluator, and Monitor agents.** | A single agent that plans, implements, evaluates, and approves its own work creates weak separation of duties and confirmation bias. Explicit role boundaries make responsibility and evidence ownership clear. | More handoffs, context transitions, and artifacts are required, but independence, control, and auditability improve. | [`CLAUDE.md`](./CLAUDE.md); [`.harness/agents/planner.agent.md`](./.harness/agents/planner.agent.md); [`.harness/agents/generator.agent.md`](./.harness/agents/generator.agent.md); [`.harness/agents/evaluator.agent.md`](./.harness/agents/evaluator.agent.md); [`.harness/agents/monitor.agent.md`](./.harness/agents/monitor.agent.md) | The SLA run demonstrated that agent boundaries operate as governance controls rather than prompt personas. Evaluator retained verdict ownership; harness/governance retained routing and progression; Monitor recorded evidence without changing outcomes. |
| **2. Make the harness configuration-driven rather than embedding application, technology, and governance rules in agents.** | Reusable agents should not contain StoreOps-, Java/Spring-, or policy-specific assumptions. Separating configuration allows the same agent model to operate against different applications and governance profiles. | Bootstrap and configuration validation become more complex, and configuration quality becomes a runtime dependency. | [`CLAUDE.md`](./CLAUDE.md); [`DESIGN_BRIEF.md`](./DESIGN_BRIEF.md); [`.harness/config/harness.yaml`](./.harness/config/harness.yaml); [`.harness/config/applications/storeops.yaml`](./.harness/config/applications/storeops.yaml); [`.harness/config/technologies/java-spring.yaml`](./.harness/config/technologies/java-spring.yaml); [`.harness/config/policies/default-governance.yaml`](./.harness/config/policies/default-governance.yaml); `.harness/output/<RUN_ID>/resolved-config.yaml` | Configuration became the harness control plane. Application, technology, and governance concerns can evolve without redefining agent responsibilities, while `resolved-config.yaml` provides immutable run-level evidence of what was actually active. |
| **3. Use Planner-derived sprint contracts as the boundary between feature intent and implementation.** | `PROMPT.md` expresses business intent but cannot safely prescribe implementation before the existing codebase is inspected. Planner discovery converts intent into repository-grounded, independently evaluable contracts. | Human approval introduces a deliberate pause before implementation, but prevents implementation based on unverified assumptions. | [`PROMPT.md`](./PROMPT.md); [`.harness/templates/spec.template.md`](./.harness/templates/spec.template.md); [`.harness/templates/sprint-contract.template.md`](./.harness/templates/sprint-contract.template.md); `.harness/output/<RUN_ID>/spec.md`; `.harness/output/<RUN_ID>/sprint-N-contract.md` | SLA planning forced lifecycle semantics, grace-period behavior, role resolution, time handling, idempotency, state tracking, architecture constraints, and tests to be resolved or surfaced before implementation. The approved contract became the stable handoff between isolated agent contexts. |
| **4. Approve and execute one sprint at a time.** | Smaller approval boundaries reduce blast radius and make implementation, evaluation, retry, and evidence easier to trace. | More human checkpoints are required than approving an entire feature at once. | [`CLAUDE.md`](./CLAUDE.md); `.harness/output/<RUN_ID>/sprint-N-contract.md`; `.harness/output/<RUN_ID>/generator-summary-iteration-N.md`; `.harness/output/<RUN_ID>/evaluator-feedback-iteration-N.md`; `.harness/reviews/<RUN_ID>/` | All Planner-derived SLA sprints were completed through bounded approval and execution stages. Sprint-level governance created a traceable relationship between approved intent, implementation, evaluation, evidence, and eventual Git changes. |
| **5. Adopt fail-closed governance for unresolved policy or mandatory evidence.** | Missing governance values must not silently become defaults because evaluation would then depend on hidden assumptions. Invalid governance should stop execution before implementation begins. | Strict validation initially blocked the SLA run and required explicit governance recovery. | [`.harness/config/policies/default-governance.yaml`](./.harness/config/policies/default-governance.yaml); [`CLAUDE.md`](./CLAUDE.md); `.harness/output/<RUN_ID>/resolved-config.yaml` | Bootstrap correctly returned `STATUS: CONFIGURATION_ERROR` when governance values were unresolved. Recovery made `failClosed` explicit, established **40/40/20** evaluation weights, **85/70** verdict thresholds, explicit hard-gate states, and `maxIterations: 3`. The failure validated the architecture rather than representing a bypass condition. |
| **6. Enable mandatory hard gates only when concrete evidence mechanisms exist.** | Declaring a quality gate without executable evidence creates false assurance. Governance must distinguish desired policy from controls that can actually be verified. | Some desirable controls remain disabled until executable tooling is available, reducing immediate enforcement breadth but preserving evidence integrity. | [`.harness/config/policies/default-governance.yaml`](./.harness/config/policies/default-governance.yaml); [`.harness/config/technologies/java-spring.yaml`](./.harness/config/technologies/java-spring.yaml); StoreOps `pom.xml`; [`.harness/agents/evaluator.agent.md`](./.harness/agents/evaluator.agent.md); [`.harness/skills/core/evaluation-framework/`](./.harness/skills/core/evaluation-framework/) | Build, tests, acceptance criteria, and governance evidence can be treated as concrete controls when evidence exists. Coverage, static analysis, architecture, or security must not be claimed merely because a tool, configuration file, skill, or extension point exists. **Policy intent is not executable evidence.** |
| **7. Use independent evaluation rather than allowing Generator self-assessment to determine success.** | The implementation agent has inherent confirmation bias. Independent evaluation provides a separate evidence path against the frozen contract and governance policy. | Re-executing checks increases execution cost and time, but materially strengthens confidence in the result. | [`.harness/agents/evaluator.agent.md`](./.harness/agents/evaluator.agent.md); [`.harness/skills/core/evaluation-framework/`](./.harness/skills/core/evaluation-framework/); [`.harness/skills/core/review-guidelines/`](./.harness/skills/core/review-guidelines/); `.harness/output/<RUN_ID>/evaluator-feedback-iteration-N.md` | Generator self-assessment remained implementation evidence rather than proof of correctness. Evaluator independently owned `PASS / CONDITIONAL_PASS / FAIL`, while retry and progression remained outside Evaluator ownership. |
| **8. Use durable, iteration-specific artifacts for context isolation and auditability.** | Agent conversations are transient and should not become the authoritative record of a governed run. Durable artifacts provide deterministic handoffs and reconstructable evidence. | Additional files, naming discipline, and archive management are required. | `.harness/output/<RUN_ID>/resolved-config.yaml`; `.harness/output/<RUN_ID>/spec.md`; `.harness/output/<RUN_ID>/sprint-N-contract.md`; `.harness/output/<RUN_ID>/generator-summary-iteration-N.md`; `.harness/output/<RUN_ID>/evaluator-feedback-iteration-N.md`; `.harness/output/<RUN_ID>/run-log.md`; `.harness/reviews/<RUN_ID>/` | Durable evidence made fresh-context evaluation practical and prevented previous iterations from being overwritten. It also separated Generator evidence, Evaluator verdicts, Monitor records, harness routing, and downstream CI/CD evidence. |
